# Отчёт о тестировании ForgeML

**Метод:** тестирование «чёрного ящика». Исходный код библиотеки не читался — тесты написаны
только по `README.md`, как это сделал бы пользователь или тестировщик, получивший библиотеку.
Каждый тест запускается в **отдельном процессе**, поэтому падение программы фиксируется как
`CRASH`, а не обрывает весь прогон.

**Окружение:** Linux x86-64, GCC 13, Release (`-O3`, OpenMP, 4 ядра); дополнительно
Debug-сборки с AddressSanitizer + UndefinedBehaviorSanitizer и с ThreadSanitizer.
Данные MNIST скачаны в `data/`.

**Как повторить:**

```bash
cmake -S . -B build && cmake --build build --target forge_qa
./build/forge_qa              # все тесты
./build/forge_qa --list       # список
./build/forge_qa deep_graph_100k   # один тест
```

> **Статус: все 9 дефектов исправлены.** Повторный прогон — **71 / 71 PASS**
> (см. раздел [«Исправления и повторное тестирование»](#исправления-и-повторное-тестирование)).

## Найденные дефекты

### 🔴 D1. Критический — программа падает на длинном графе вычислений

**Тесты:** `deep_graph_100k` (CRASH), `deep_graph_1m_forward_only` (CRASH)

```cpp
auto x = Tensor::full({}, 1.0f).requires_grad_();
Tensor y = x;
for (int i = 0; i < 100000; ++i) y = y + 1.0f;
y.backward();          // Segmentation fault
```

Падают **две** операции:

| Что | Падает при глубине графа (Linux, стек 8 МБ) | Оценка для Windows (стек 1 МБ) |
|---|---|---|
| `backward()` | между 60 000 и 100 000 операций | **≈ 10 000** |
| удаление графа (даже без backward) | между 100 000 и 200 000 | **≈ 15 000–20 000** |

Оценка для Windows получена запуском с `ulimit -s 1024`. ASan подтверждает: `stack-overflow`.
Это не исключение, а аварийное завершение процесса — пользователь не может его поймать.
**Ожидание:** длинные цепочки (RNN по длинной последовательности, цикл из многих шагов)
работают, как в PyTorch. Граф из 10 000 операций проходит.

*Для разработчика:* похоже на рекурсию глубиной в длину графа — и в обходе графа при
backward, и в цепочке деструкторов `shared_ptr` при удалении.

### 🟠 D2. Высокий — арифметика с пустыми тензорами бросает исключение

**Тесты:** `empty_tensor_arithmetic` (FAIL), побочно `layer_construction_errors`

```cpp
Tensor::zeros({0, 3}) * 2.0f;                    // invalid_argument:
                                                 // "expand(): cannot expand [0, 3] to [1, 3]"
Tensor::zeros({0, 3}) + Tensor::ones({3});       // то же
broadcast_shapes({0}, {1});                      // возвращает [1], должно быть [0]
```

**Ожидание:** результат формы `[0, 3]` (так в NumPy/PyTorch: ось размера 1 растягивается до 0).
При этом `sum`, `matmul`, печать пустых тензоров работают (`empty_tensors` — PASS).
Риск: пустой батч или пустой фильтр данных роняет обучение.

### 🟡 D3. Средний — `sum(x, dim)` и `mean(x, dim)` теряют точность на длинных осях

**Тест:** `long_sum_precision` (FAIL)

```cpp
auto x = Tensor::full({1, 10000000}, 0.1f);
sum(x).item();      // 1 000 000      ✓
sum(x, 1).item();   // 1 087 937      ✗ ошибка 8.8 %
```

Полная сумма точна, а сумма по оси — нет: одна и та же математика даёт разный ответ.
На обычных размерах (сотни–тысячи элементов) ошибка незаметна; проявляется на длинных осях.

### 🟡 D4. Средний — неудачная `load()` портит модель наполовину

**Тест:** `failed_load_leaves_model_intact` (FAIL)

```cpp
nn::Sequential a;  a.add<nn::Linear>(3, 4);  a.add<nn::Linear>(4, 2);  a.save("a.bin");
nn::Sequential b;  b.add<nn::Linear>(3, 4);  b.add<nn::Linear>(4, 5);
b.load("a.bin");   // исключение — правильно, архитектуры разные...
                   // ...но первый слой b уже перезаписан весами из файла
```

**Ожидание:** при ошибке модель остаётся в исходном состоянии (загрузка «всё или ничего»).
Сейчас после пойманного исключения модель находится в смешанном, бессмысленном состоянии.

### 🟡 D5. Средний — гонка данных в генераторе случайных чисел

**Тест:** `parallel_independent_training` — PASS в Release, но **ThreadSanitizer сообщает
`data race`** в `std::mersenne_twister_engine` при вызове из `Tensor::rand` (через конструктор
`nn::Linear`) в нескольких потоках одновременно.

README не обещает потокобезопасность, но и не предупреждает. Последствия гонки —
неопределённое поведение: невоспроизводимые веса, теоретически — порча состояния генератора.
**Ожидание:** либо генератор защищён (или свой на каждый поток), либо в README явно сказано,
что создавать модели из разных потоков одновременно нельзя.

Сам режим `NoGradGuard` корректно действует только на свой поток (`no_grad_is_per_thread` — PASS).

### 🟢 D6. Низкий — `max` игнорирует NaN

**Тест:** `nan_propagation_in_max` (FAIL)

```cpp
max(Tensor::from_vector({1, NAN, 3}, {1, 3}), 1).item();   // 3, ожидалось NaN
```

PyTorch и NumPy возвращают NaN. Проглатывание NaN может скрыть «взорвавшееся» обучение:
loss выглядит нормально, хотя внутри сети уже NaN.

### 🟢 D7. Низкий — изменение весов между forward и backward даёт тихо неверный градиент

**Тест:** `modify_after_forward` (FAIL)

```cpp
auto w = Tensor::from_vector({1}, {1}).requires_grad_();
auto loss = sum(w * w);     // при w = 1 производная 2
w.data()[0] = 10;           // изменили вес до backward
loss.backward();
w.grad().item();            // 20 — посчитано для нового значения, без предупреждения
```

PyTorch в этой ситуации бросает ошибку («a variable needed for gradient computation has been
modified by an inplace operation»). Здесь ошибки нет, градиент молча не соответствует forward.
Типичный случай — `optimizer.step()` по ошибке вызван между forward и backward.

### 🟢 D8. Низкий — `cross_entropy` молча принимает дробные метки

**Тест:** `loss_errors` (FAIL на последней проверке; остальные 5 проверок — PASS)

```cpp
nn::cross_entropy(logits, Tensor::from_vector({0, 1.5f}, {2}));   // работает, 1.5 -> класс 1
```

Отрицательные метки, метки вне диапазона и неверное число меток корректно отклоняются.
Дробная метка почти всегда означает ошибку в данных (например, перепутаны тензоры) —
лучше сообщить о ней.

### 🟢 D9. Низкий — непонятное сообщение для `Linear(0, 5)`

**Тест:** `layer_construction_errors` (FAIL на проверке текста сообщения)

`nn::Linear(0, 5)` бросает исключение, но с текстом
`expand(): cannot expand [0, 5] to [1, 5]` — о внутренностях, а не о том, что `in_features`
не может быть 0. По сути это побочный эффект D2. Остальные проверки группы
(`Dropout(1.0)`, `Dropout(-0.1)`, оптимизатор с неподходящими тензорами) — PASS.

## Что работает хорошо

- **Все примеры из README** работают и дают обещанные значения.
- **Математика:** `matmul` совпадает с наивным расчётом на 7 наборах размеров (включая 1×1,
  257×129·129×65 и транспонированные входы); редукции по каждой оси 3D-тензора; 6-мерные
  тензоры; `softmax` устойчив к сдвигу и к логитам ±10 000; `sigmoid`/`tanh` без NaN на ±1000;
  `log(0)`, `1/0`, `0/0` дают `-inf`, `inf`, `nan`, как в IEEE.
- **Autograd:** производные из учебника, градиент cross-entropy точно равен
  `(softmax − one_hot)/N`, независимая численная проверка сети `tanh(xW+b)·sigmoid`, цепочки
  views, повторно используемый слой, накопление, `detach`, вложенные `NoGradGuard` и
  восстановление режима после исключения.
- **Ошибки пользователя:** из ~45 намеренно неправильных вызовов (пустой тензор, неверные
  индексы, формы, оси, `backward` без `requires_grad` и т.д.) все, кроме двух случаев
  (D8, D9), отклоняются **понятным исключением**, программа ни разу не упала.
- **Обучение:** линейная регрессия находит `w = 3, b = −2`; Adam восстанавливает матрицу 3×2;
  классификация «кучек» ≥ 97 %; на «трёх спиралях» линейная модель проваливается, а MLP
  даёт ≥ 95 % (сеть действительно учится нелинейному); momentum в 33 раза лучше обычного SGD;
  weight decay, `lr = 0`, Dropout в train/eval; **MNIST — ≥ 93 % за одну эпоху** (≈ 5 с).
- **Файлы:** сохранение → загрузка даёт побитово одинаковые предсказания; пустой, мусорный,
  обрезанный файл, файл с длиной имени ≈ 9·10¹⁸, несуществующий файл и папка — понятные ошибки.
  Самодельные IDX-файлы читаются правильно; перепутанные/обрезанные — отклоняются.
- **DataLoader:** за эпоху каждый пример ровно один раз, входы и метки не перепутываются,
  неполный последний батч, одинаковый seed → одинаковый порядок.
- **Ресурсы:** 3 000 шагов обучения — рост памяти < 5 МБ; промежуточные тензоры освобождаются
  после выхода `loss` из области видимости; `matmul` 512³ — 0.03 с; прямой проход 10 000×784 — 0.15 с.
- **Санитайзеры:** под AddressSanitizer + UBSan — ни одной ошибки памяти, утечки или
  неопределённого поведения (кроме переполнения стека из D1).

## Ошибки самого тестировщика (исправлены в ходе работы)

- `momentum_helps`: сначала требовал, чтобы momentum был «в 100 раз лучше» — порог взят
  с потолка. Фактически он лучше в 33 раза, это нормальное поведение; порог исправлен на 10×.
- `layer_construction_errors`: тест `Linear(0, 5)` сначала проходил **случайно** — исключение
  было, но не по той причине. Проверка уточнена (теперь смотрит текст сообщения), что и
  выявило D2/D9.
- Под ASan тесты `no_memory_leak_in_training` (рост 328 МБ) и `big_batch_forward` (3.1 с) не
  проходят — это артефакты санитайзера (карантин освобождённой памяти и замедление в разы),
  а не дефекты: в Release оба теста проходят.

## Что не проверялось

- Сборка и запуск на Windows/MSVC — в тестовом окружении их нет (глубина падения D1 для
  Windows оценена эмуляцией стека 1 МБ).
- Скрипт `scripts/download_mnist.ps1` — нет PowerShell.

## Исправления и повторное тестирование

| Дефект | Было | Что исправлено | Стало |
|---|---|---|---|
| 🔴 D1 | CRASH на графе ≈ 10 000 операций (Windows) | обход графа в `backward` — явным стеком; длинная цепочка узлов удаляется циклом в `Node::~Node()` | граф из **1 000 000** операций: backward и удаление работают даже при стеке 1 МБ |
| 🟠 D2 | `zeros({0,3}) * 2` — исключение | правило broadcasting: ось размера 1 растягивается до размера другой, **включая 0** | форма `[0, 3]`, как в NumPy |
| 🟡 D3 | `sum(x, 1)` = 1 087 937 вместо 10⁶ | редукции по оси накапливают сумму в `double` | 1 000 000 (ошибка < 1) |
| 🟡 D4 | неудачный `load()` портил модель | файл сначала целиком читается и проверяется во временные буферы, только потом копируется; добавлены лимиты на длину имени и число осей | при ошибке модель не меняется |
| 🟡 D5 | ThreadSanitizer: data race | доступ к общему генератору защищён `std::mutex` | ThreadSanitizer: 0 предупреждений |
| 🟢 D6 | `max([1, NaN, 3])` = 3 | NaN «заразен» в `max`, `argmax` возвращает индекс NaN | NaN, как в PyTorch |
| 🟢 D7 | градиент тихо неверный (20 вместо 2) | счётчик версий в `Storage`; узел запоминает версии входов, backward сверяет | понятная ошибка «input … was modified after the forward pass» |
| 🟢 D8 | метка 1.5 молча = класс 1 | проверка, что метка — целое число (и не NaN) | исключение с текстом |
| 🟢 D9 | `Linear(0, 5)`: «cannot expand [0, 5]…» | проверка размеров в конструкторе `Linear` | «Linear: in_features and out_features must be > 0» |

**О D7.** Изменением считается доступ через неконстантные `Tensor::data()` и `Tensor::at()`.
Внутренний код библиотеки переведён на константный доступ там, где он только читает,
чтобы не было ложных срабатываний. Обычный цикл обучения (`zero_grad → forward → backward →
step`), печать, `item()` и чтение через `const Tensor&` ошибку не вызывают — это проверено
отдельным тестом `regression_d7_reading_is_not_modification`. Описано в README.

**Исправление в самом QA-наборе.** Тест `modify_after_forward` по описанию принимает
«правильный градиент **или** ошибку», но код теста принимал только первый вариант;
исправлен, чтобы соответствовать своему описанию.
